## Context

本プロジェクトは Tauri（Rust backend）+ Svelte（TypeScript frontend）で構築されたデスクトップアプリケーションである。現在、tokscale CLI の `--json` 出力を手動でターミナルで確認しており、特定の利用プラン（Goプラン相当）のコストリミット状況を可視化する仕組みがない。本変更では、tokscale の実行結果を自動取得し、3 つのローリングウィンドウ（5時間/週間/月間）の残予算と次の空き枠をリアルタイムで表示する。

## Goals / Non-Goals

**Goals:**
- Rust バックエンド経由で `tokscale --json --no-spinner` を安全に実行し、生 JSON をフロントエンドに供給する。
- PlanConfig（対象モデル・各ウィンドウ上限）を拡張可能な形で定義し、将来のプラン変更に対応できる基盤を作る。
- フロントエンドでローリングウィンドウ（5時間/1週間/30日間）の cost を集計し、残予算と使用率を算出する。
- 使用率 80% を超えたウィンドウを警告色で可視化する。
- 5時間ウィンドウの「Next Free Slot」（最も古いセッションが外れるまでの概算時間）を計算・表示する。
- 60 秒ごとの自動更新ポーリングを実装する。
- SmartHR Design System（DESIGN.md）のカラー・タイポグラフィ・レイアウト原則に従った UI を構築する。

**Non-Goals:**
- tokscale CLI 自体の改変や機能追加。
- 複数プランの同時監視（今回は単一プラン設定のみ）。
- ユーザーが UI 上でプラン上限を編集する機能（現時点では TypeScript の定数としてハードコード）。
- 履歴データの永続化（LocalStorage/DB 等は使わない）。
- アラート通知（OS ネイティブ通知や Slack 連携等）。
- チャートライブラリの導入（SVG 自前実装で済ませる）。

## Decisions

### 1. バックエンドで CLI を実行
- **Decision**: `tokscale` の実行は Rust 側（`std::process::Command` または Tauri の `Command` API）で行い、結果を文字列としてフロントエンドに返す。
- **Rationale**: Tauri のセキュリティモデルでは、フロントエンドから直接シェルコマンドを実行することが推奨されない。また、将来的に tokscale の出力後処理を Rust 側で行う拡張性も確保できる。
- **Alternatives considered**: フロントエンドから `fetch` 相当で HTTP API を叩く案 → tokscale が HTTP API を提供していないため不可。

### 2. 集計ロジックをフロントエンドに配置
- **Decision**: JSON のパース・フィルタリング・集計はフロントエンドの TypeScript で行う。
- **Rationale**: tokscale の JSON 出力はセッション数が少なく（数十〜数百件程度）、フロントエンドでの計算コストは無視できる。バックエンドで型付け構造体を作るまでの工数を削減し、UI ロジックとデータ処理を同じ言語で書くことで保守性を高める。
- **Alternatives considered**: Rust 側で構造体にデシリアライズして集計した上でフロントエンドに渡す案 → 現状では過剰。将来データ量が増えた場合は検討する。

### 3. SVG によるドーナツチャート自前実装
- **Decision**: ドーナツチャートは軽量な SVG で直接描画し、外部チャートライブラリは導入しない。
- **Rationale**: 描画内容は円弧の割合表示と中心テキストのみで非常に単純。ライブラリを追加するとバンドルサイズが増え、SmartHR Design System の独自色指定との整合も面倒になる。
- **Alternatives considered**: Chart.js / D3.js / recharts の導入 → 不要な複雑性。

### 4. PlanConfig を TypeScript 定数として管理
- **Decision**: 対象モデル一覧とウィンドウ上限は、現時点では TypeScript のオブジェクト定数としてフロントエンドに配置する。
- **Rationale**: 今回のスコープではユーザーによる動的なプラン変更は不要。将来的に複数プランを切り替えたい場合は、この定数を JSON 設定ファイル化するだけで対応可能。

### 5. ウィンドウ境界値の定義
- **Decision**: ローリングウィンドウの範囲は「現在時刻 - ウィンドウ期間 <= session.date < 現在時刻」とする（左閉右開）。
- **Rationale**: ちょうど 5時間前のセッションは含め、現在時刻より未来のセッションは除外する。これにより「5時間前に発生したセッションはまだウィンドウ内」という直感に合致させる。

## Risks / Trade-offs

- **[Risk] tokscale コマンドが PATH に存在しない、または実行権限がない**  
  → **Mitigation**: Rust 側で `Command` 実行エラーをキャッチし、フロントエンドに分かりやすいエラーメッセージを返す。UI 上にも手動更新ボタンを配置し、エラー時の再試行を容易にする。

- **[Risk] ISO8601 日付のパースでタイムゾーン誤差が発生する**  
  → **Mitigation**: `new Date(isoString)` で UTC としてパースした後、ローカル時刻のタイムスタンプで比較する。集計ロジック内では全て `Date.getTime()`（ミリ秒単位のエポックタイム）で演算し、JST 等のローカルタイムゾーンの差異を吸収する。

- **[Risk] フロントエンドでの頻繁なポーリングが不要な CPU 負荷を生む**  
  → **Mitigation**: 60 秒間隔は現実的な頻度。ウィンドウが切り替わるタイミング（5時間後等）を厳密に追う必要はなく、概算で十分なユースケースであるため、これ以上の短縮は行わない。

- **[Trade-off] 集計をフロントエンドで行うため、大規模データ（数万件以上）に弱い**  
  → **Acceptance**: tokscale の利用状況から、1 ヶ月分でも数百件を超えることは稀と想定。万が一ボトルネックになった場合は Web Worker への移行、または Rust 側への計算移譲を検討する。

## Migration Plan

- 本変更は新規機能追加であり、既存コードへの破壊的変更はない。
- マージ後、`src-tauri/src/lib.rs` にコマンドを追加し、Tauri の `invoke` ハンドラを登録する。
- フロントエンドでは新規コンポーネントを追加し、`src/routes/+page.svelte` 等の既存ページに組み込む。
